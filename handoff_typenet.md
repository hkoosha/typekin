# Handoff: typenet reimplemented with typekin

Working notes for resuming the typenet × typekin investigation. Line numbers and
re-run results are for typekin `27fbdab` ("fix make fn const regression");
findings recorded before that commit say so where it changed them.

## Goal

The user, typekin's author, asked what would happen if `arena/typenet` (a
userspace IPv4/ICMP/TCP/UDP stack; workspace crates `stack`, `server`,
`loadgen`, `utils`) were reimplemented with typekin:

1. How much handwritten Rust (KLOC) would decrease.
2. How much faster it would be.
3. How much safer it would be.

The user had already prototyped the idea in `examples/my_tcp.rs`. A follow-up
round asked:

- whether generated `unsafe` exists without `unsafe` friends, and whether
  typekin's `unsafe` "counts";
- what a panic-free mode would require, including whether operators can return
  `Result<Foo, ()>`;
- what the "fragile workaround" in the port is.

Both rounds were answered. Afterwards the user committed `27fbdab`, which
removes generated `unsafe` code and makes unvalidated `make` const. No task is
open.

## The port

Only `stack/src/protocol/tcp/seq_space.rs` was ported: it is typenet's one
module of single-primitive newtypes with arithmetic, the domain `my_tcp.rs`
covers. Three scouts (header codec, TCP logic, server/utils) catalogued the
rest, which was reasoned about rather than ported.

typenet's generic `SeqOffset<T, D>` became three types to keep its distinctions
(length, signed difference, window); one `i32` type, as in `my_tcp.rs`, would
lose them. Declarations in
`/tmp/tk-typenet/port/stack/src/protocol/tcp/seq_space.rs`:

```rust
#[typekin::circular(
    hide_in = none,
    with = core_int,
    without = math_add,
    produce = Self::diff(_) -> SeqDiff<D>,
    facet = circular {
        with = math_add,
        produce = Self,
        friend = Self::len_raw(SeqLen<D>) -> Math,
    },
)]
pub(super) struct SeqPoint<D: Direction>(u32);

#[typekin::delta(hide_in = none)]
pub(super) struct SeqDiff<D: Direction>(i32);

#[typekin::delta(hide_in = none, friend = _(SeqWnd<D>) -> Make)]
pub(super) struct SeqLen<D: Direction>(u32);

#[typekin::int(hide_in = none, without = [self_math, self_bit])]
```

### 3. Safety

typenet bugs that validated header types could reject; the port doesn't touch
them:

- IPv4 IHL < 5 is accepted (`ipv4_header.rs:76`,
  `usize::from(ip_hdr[0] & 0xF) * 4`, no lower bound). A probe parsed an IHL = 4
  header with the payload starting at byte 16.
- TCP data offset < 20 is accepted (`tcp.rs:181`, `tcp_hdr[12] >> 4 << 2`;
  verified by reading only). An offset past the end of the data silently becomes
  an empty payload.
- Scout-reported, not re-verified: total length is unchecked, fragments are not
  rejected, the UDP length field is not read, and config values are not
  validated.

Behaviour change: typekin's `precedes` is
`let d = rhs.wrapping_sub(lhs); d != 0 && d < half`, while typenet's is
`(self - other) as i32 < 0`, under which antipodes precede each other. With a
forged ACK (ack = snd_nxt + 2^31), base replies with a duplicate ACK and the
port drops silently; state stays intact in both.

Lints:

- Generated `panic!` and `unsafe` are invisible to `clippy::panic` and
  `unsafe_code`.
- Leaks from typekin output under typenet's wall:
  - `clippy::missing_safety_doc` on every type: every protocol declares
    `unsafe trait Unsafe`, and clippy doesn't see its generated `# Safety` doc.
    Still fires at `27fbdab`.
  - `clippy::expl_impl_clone_on_copy` on generic types whose parameters are
    `Copy`-bounded (typenet's `Direction: Copy`). Still fires at `27fbdab`.
  - `clippy::manual_range_contains` on range domains such as `5..=15`. Not
    re-checked at `27fbdab`.

The four seq types expand to 4,053 lines (rustfmt-normalized): 328 `pub fn`, 14
`panic!` sites (8 const-evaluated layout asserts, 4 `map`, 2
`_result_or_panic`), all unreachable without a domain, 4 `unsafe trait Unsafe`
declarations, and no `unsafe` blocks. `27fbdab` changes only the four `make`
lines.

### 4. Generated `unsafe`

Before `27fbdab`:

- `NonZero` storage (a domain excluding zero) built validated values with

  `NonZero` or `Wrapping` storage.
- Every friend protocol declares `unsafe trait Unsafe`. `unsafe impl` and

- The seq types contained no `unsafe` operation, only the four trait
  declarations.
- `/tmp/tk-typenet/ubprobe`, a `#![forbid(unsafe_code)]` crate, reached

### 5. Panic-free mode

Panic sources and how a panic-free mode could avoid them:

| Source                     | Where it's generated                                                                                                                                                                                                                       | Panic-free alternative                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Domain check fails         | `make`/`of` with untrusted friends; operators and `+=`; `map` (`integral_items.rs:491`); forwards returning `Self` such as `wrapping_add`, `pow`, `from_be_bytes` (`integral_forward.rs:473`); bitflag `from_bits*` (`bitflag.rs:529`); text `+` (`text.rs:648`) and untrusted text friends (`text.rs:923`) | Return `Result`/`Option`; `try_make`, `try_map`, `checked_*` already do |
| The arithmetic itself      | `/` and `%` by zero; `MIN / -1`; `sequential` overflow (`zz_profile_integral.rs:99`); checked `Neg` (`integral_items.rs:769`); `int` overflow in debug builds                                                                               | A divisor type excluding 0, a wrapping/saturating profile, or `Result` |
| Zero into `NonZero`        | `storage_expression` (`integral.rs:792`), reached by blind trust and, at `27fbdab`, by a wrong `_proven`/`_within`                                                                                                                         | `Result`, or plain storage                                            |
| Present but unreachable    | `Ord::cmp` via `partial_cmp().unwrap()` (`integral_impls.rs:621`, `integral_items.rs:867`); packed getter re-check (`packed.rs:951`); `_result_or_panic` on unvalidated types; packed `make` with `non_zero` (only through blind-trusted fields) | `Ord::cmp` on the raw value; proven construction                      |
| Debug-only or compile-time | `debug_assert!` in `_proven`, `_within` and packed `make`; layout asserts; literal macros; proof constants (`packed.rs:1217`)                                                                                                               | Already fine                                                          |

Rule: generate an infallible signature (`-> Self`, `Output = Self`, `+=`) only
where typekin proves the operation total; otherwise make it fallible or leave it
out. An explicit request that can't be proven is an error, as with
`prove = [...]`.

Today's closure proofs aren't strong enough. They show that every result that
exists is valid: the `Checked` policy treats overflow, zero divisors, `MIN / -1`
and oversized shifts as "no value" (`zz_domain_closure.rs:59`, applied at
`:349`). A proven checked `+` can still overflow, and a proven `/` can still
divide by zero. Totality needs:

- the unclamped result range inside the type range, or a wrapping/saturating
  policy;
- divisors whose domain excludes 0, and also −1 when `MIN` is admitted;
- shift amounts below `BITS`.

With `NonZero` storage, a proven operation needs either `new_unchecked` or a
panic arm; avoiding both means plain storage (`without = non_zero`).

`Result` outputs, checked with rustc in `/tmp/tk-typenet/orphan_probe.rs`
(output: `Ok(Foo(95))`, `Err(())`, `Err(())`):

- `type Output = Result<Foo, ()>` works, and so does `(a + b)?`.
- `impl Add<Foo> for Result<Foo, ()>` is allowed, including the generic
  `impl<D> Add<G<D>> for Result<G<D>, ()>`, so `a + b + c` chains.
  `impl Sum<Foo> for Result<Foo, ()>` is allowed too.
- `impl Add<Result<Foo, ()>> for Result<Foo, ()>` fails with E0117, so
  `(a + b) + (c + d)` needs `?` on one side.
- `?` inside `add_assign` fails with E0277: there is no fallible `+=`.
- Generic code bounded on `Add<Output = Self>` won't accept such a type.

Proposed shape: per operator and right-hand type, `Output = Self` when total,
otherwise `Result<Self, ()>` plus `Result<Self, ()> + Rhs` impls for chaining;
no `+=` unless total; `try_map` instead of `map`; `Ord::cmp` on the raw value
instead of `partial_cmp().unwrap()`. typenet's seq types have no domain and
wrap, so their `+` and `-` are already total.

### 6. The fragile workaround

typenet builds seq values in const contexts
(`const SYN_BYTE_OUT: … = SeqOffset::new(1);`, fixtures such as
`CLIENT_ISN.const_add(SYN_BYTE_IN)`). Before `27fbdab`, no typekin constructor
was both `const` and lint-clean:

- `make` wasn't `const` on stable (`make → of → <T as Make>::make`).
- `try_make` is `const` but returns `Result`. Unwrapping it needs `panic!`,
  which `clippy::panic = forbid` rejects even inside a `const fn` (tried in
  `port2`).

So the port has `hide_in = none` and, on each type (`seq_space.rs:27`, `:57`,
`:65`, `:81`):

```rust
impl<D: Direction> SeqLen<D> {
    pub(super) const fn new(primitive: u32) -> Self {
        Self(primitive, PhantomData)
    }
}
```

It is fragile because:

1. It depends on generated code. One field is declared but two are built,
   because typekin appends a `PhantomData<D>` marker. It breaks if that marker
   changes shape or if storage becomes `Wrapping<u32>` (`wrapping`) or
   `NonZeroU32` (a domain excluding zero).
2. It turns off `hide_in`, the invariant boundary. On a validated type the same
   constructor silently skips validation.

The lint-clean alternative found before `27fbdab` (`constprobe`):

- constants via `with = lit_macro` on the unvalidated types
  (`seq_point!([Out] 400)`, `seq_len!([Out] 1)`): the macro's panic happens
  during const evaluation, which clippy accepts;
- runtime values via `make`, which can't panic without a domain;
- non-`const` `produce` callbacks (`SeqDiff::make(..)`);
- const arithmetic via
  `SeqPoint::from_be_bytes(ISN.raw().wrapping_add(SYN.raw()).to_be_bytes())`,
  which needs `core_int` (`wrapping_add` takes `Self`, not the raw value);
- with default `hide_in`, `clippy.toml` names the hidden paths, such as
  `protocol::tcp::seq_space::__seq_point::SeqPoint`;
- `#![expect(clippy::missing_safety_doc, reason = "Generated by typekin")]`.
  `expl_impl_clone_on_copy` didn't fire there because its `Direction` has no
  `Copy` bound.

At `27fbdab`, unvalidated `make` is
`pub const fn make(it) -> Self { return Self::_or_panic(it); }`
(`integral_items.rs:380`), and `_or_panic` has no panic arm without validation
(`integral_items.rs:946`). Consequences:

- The port's `new` and `hide_in = none` should be replaceable by `make`. Not
  tried.
- `constprobe` now fails clippy with two `missing_const_for_fn` (`src/lib.rs:22`
  `diff`, `:47` `parse`): functions that only call `make` can now be `const`.
  Its `lit_macro` constants and `from_be_bytes` round trip are probably
  unnecessary now. Not tried.
